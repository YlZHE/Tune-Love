# 保留 libkeyfinder：输入链路准确度排查

## 结论

本轮严格按“提高现有识别准确度，不寻找替换引擎”执行。所有调性判断仍使用固定版本 libkeyfinder 2.2.6 的特征提取、原始大小调模板与分类器。没有改生产引擎、GUI、音频采集、投票规则或 Auto-Tune 控制。

完成三项有区分变量的离线排查：

1. **避免归一化截波：** 没有提高本批样本的正确确认数；不能把波形更完整宣称成识别更准。
2. **识别前做谐波／打击乐分离：** 两批诊断样本均退步，不采用默认 HPSS 前处理。
3. **左右声道先提取特征再合并：** 修复了一个可复现的局部相位抵消用例，但在真实样本上仍退步，不能全局启用。

因此，本轮**没有得到可以安全接入主程序的整体准确度提升**。找到的是一个具体信息损失机制与可运行实验原型，不是已经解决真实歌曲准确度问题。

## 数据与对照

- 沿用已明确下载的两批 FMA/FMAKv2 音频：48 首与 46 首，合计 94 首、94 位艺人。两批已被反复分析，均不是新留出集。
- 参考是歌曲／选段级标签，不是独立人工标注的每个六至八秒窗口；下文“正确”指与该参考标签完全一致，主音与大小调都必须一致。
- 每首只观察第 6–12 秒的七个窗口，共 658 窗口；每窗最多八秒，初始三票、替换五票未改。未读取当前端点以后的音频，没有为短音频填充出新观测。
- 保留原有 RMS 静音门限；没有新增“不确定就不输出”的门控来美化正确比例。
- 不扫描用户曲库、不新开采集、不上传或保存采集 PCM。输入来自两个既有明确清单，复用现有受限 FFmpeg 解码入口。
- 原样编译现有 C++ 桥接和固定上游源代码为离线 DLL。对照适配器的全部 658 个原始候选与历史探针相同，24 维分数最大差约 `9.99e-16`。这验证了实验入口，没有把新适配器直接当作正确基线。

## 总体结果

|---|---:|---:|
| 当前增量流程 | 32 / 34 / 28 | 38 / 54 / 2 |

|---|---:|---:|

HPSS 相对生产对照有 2 首由未正确确认变为正确，但 8 首反向变化；声道特征均值没有新增正确确认，丢失了 2 首。不能仅展示局部改善的案例。

## 1. 截波是否导致误判

现有 `engine.rs` 将输入归一化至目标 RMS，再硬限制到 `[-1,1]`；`stream.rs` 遇到将会截波的窗口退回批处理。纯比例缩放和硬截波是两个不同操作，因此实验分别控制了波形变化与流式重置。

658 个窗口中有 160 个会触发原来的截波条件。将增益限制到峰值不超过 0.98 后：

- 同为批处理时，658 个候选与原截波版本全部一致。
- 移除流式截波回退后，有 7 个窗口候选与原增量流程不同，但第 8／12 秒的正确、错误、未确认数量均未改变。不能把这些变化归因于波形去失真；其中还包含 FFT 网格和重置路径的变化。

结论仅限本批样本：截波存在，但尚不是这里准确度不足的主要证据。没有为此修改生产代码。

## 2. 谐波／打击乐分离

查阅并复用 [Librosa 0.11.0 色度特征增强示例](https://librosa.org/doc/0.11.0/auto_examples/plot_chroma.html)及其 [HPSS 实现](https://github.com/librosa/librosa/blob/0.11.0/librosa/decompose.py)。Librosa 只用于音频前处理，**不负责调性判断**。

固定一次配置，没有在已看过的样本上遍历参数：

- `librosa.effects.harmonic`
- `n_fft=2048, hop_length=512, kernel_size=31, power=2, margin=1`
- 每次仅处理当时已有的六至八秒窗口，然后交给原来的 libkeyfinder 批处理入口。
- 使用无截波批处理作为控制组，分离前处理与增量／批处理差异。

持续音加短促宽带噪声的受控测试通过：保持持续音能量，同时降低噪声段能量。但**清理信号成功不代表调性判断更准**。两组真实音乐结果均退步，当前不采用这组默认前处理；也不能由此推断所有 HPSS 参数或所有音乐类型都无效。

实验调用中位约 487 ms，最大约 2.17 s；包括 Python 前处理和原生分析，不包括采集、IPC 与 GUI。首次依赖初始化期间，独立单元测试曾耗时约 204 秒，后续暖运行显著缩短。这些是研究环境现象，不是主程序性能验收。

## 3. 局部相位抵消：明确的机制，尚非通用修复

现有声道策略：先试左右波形平均；只有平均 RMS 小于较强声道的 25% 时才改用单侧。它能防护整段强反相，却不保证保留每个音高上的信息。

受控重现：

1. 使用实验室既有的 C 大调和声进程。
2. 左声道为“居中噪声 + 和声”，右声道为“居中噪声 − 和声”。
3. 平均后和声抵消，而居中噪声仍有足够 RMS，因此旧门限仍选择平均声道，原判断偏离 C 大调。
4. 对左右声道分别调用原生 `progressiveChromagram` / `finalChromagram`，合并各自 72 维特征，再用原生 `KeyClassifier` 与原模板分类，恢复 C 大调。

这里没有新写一套频谱、调性提取或分类算法，只改变了声道合并所在的阶段。还验证了：

- 右声道整体反相不再改变合并后的分数；
- 双单声道的结果和分数与原引擎一致；
- 非有限数、错误声道数、过短输入仍拒绝。

但在 94 首真实诊断样本上，全局使用声道特征均值从 38 首降到 36 首，因此**不能把受控用例修复当作普遍提升并直接发布**。该原型目前只保留为定位相位抵消问题的实验工具。其约 47 ms 的离线中位调用时间也不代表完整生产延迟。

## 下一步的研究范围

本轮三个输入层方案均未带来整体提升，接下来不继续盲目叠加滤波、换引擎或调低确认门槛。应先围绕具体误判歌曲区分两类原因：

1. **输入丢失了关键音高：** 比较声道、频段与原生特征，验证是否确有局部抵消或强干扰；声道特征原型用于诊断，不自动全局接管。
2. **关键音高存在，但主音／大小调排序不对：** 检查多个时间片中的和声证据及正确候选排名，再决定是否需要在现有特征和模板接口内做针对性改进。普通分数平均和单纯增加等待时间在此前研究中已经暴露局限，不重复当作已知有效方案。

新增决策规则或学习模板之前，需要独立标注的失败片段与未用于调参的新验证集。仍然复用 libkeyfinder，且每项改动都应同时报告修正和退步，而不是只报告正确数或拒答后的条件准确率。

## 交付与核验

实验均位于 `artifacts/key-engine-evaluation/native-input-study-20260930/`，不属于部署路径：

- `normalization.json`：四路归一化／批处理控制及完整分数。
- `harmonic.json`：HPSS 逐窗结果、配置和对照。
- `stereo.json`：声道特征均值、对照与逐窗分数。
- `native_input.py`、`harmonic_input.py`、`stereo_input.py`、`stereo_lab.cpp`：离线诊断原型。
- `run.mjs`、`run-harmonic.mjs`、`run-stereo.mjs`：受限输入、已有清单、拒绝覆盖历史输出的重放脚本。实际本轮只运行到第 12 秒；`run-stereo.mjs` 的 30 秒选项未在本轮执行。
- `input-tests-v2.log`：13 项前处理／边界／原生一致性测试通过。
- `lab-regression.log`：既有实验工具 17 项回归通过；其中旧引擎 worker 仅做兼容性回归，不进行替换引擎比较。

使用已读的 `systematic-debugging` 流程先复现、再单变量验证；按 `test-driven-development` 先建立失败检查、再实现实验适配。最终是否可用以真实对照结果为准，不以单元测试数量代替准确度。

主程序 debug／release 文件、前端及音频／识别相关的 15 个既有保护文件与前轮哈希一致。没有发布新 GUI 版本，没有操作用户播放器或宿主，没有改写历史研究结论。
