# 实时去人声播放链路（子项目 1：接管与回放主干）设计

日期：2026-10-02。状态：设计已逐段获用户确认，待审阅书面稿。上游依据：[AGENTS.md 路线更新](../../../../AGENTS.md)、[可行性探测](../../../../work/devocal-spike-20261002/README.md)、[去人声候选本机实测](../../../../docs/2026-10-02_separation-bench-report.md)、[权重许可](../../../../docs/2026-10-02_model-weights-licensing.md)。

## 1. 目标与成功标准

去人声是产品核心：用户听到的是播放器正在播放的歌曲去掉原唱后的伴奏，同时看着原播放器的歌词跟唱。

用户提出的约束：
- 不得为了换取前瞻而整体延迟播放，只允许很小的处理延迟；
- 兼容各种播放器，不依赖具体宿主；不用 loopMIDI、额外插件或针对某个宿主的脚本；
- GPU 可选，CPU 路径必须可用；要有面向弱电脑的档位；不能跑满 CPU/GPU；
- 分离模型要有多个选项。

本子项目（第一版）的成功标准：

| 项目 | 标准 |
|---|---|
| 通用性 | 任何通过 Windows 媒体会话识别到的播放器都可以接管，不需要驱动、注入或在播放器里装插件 |
| 直通延迟 | ≤ 40 ms（实测：系统输出与源信号互相关） |
| 去人声延迟（StemgenRT） | ≤ 50 ms |
| 稳定性 | 连续 60 秒 0 断音（10 ms 块中的能量骤降计为一次断音） |
| 不会“没声音” | 引擎或应用任意一方异常退出，播放器音量都能恢复；最坏情况（两者同时退出）在下次启动应用时恢复 |
| 可承受 | CPU 不够时自动退回原声直通并提示用户，不跑满 CPU |

## 2. 可行性依据（探测，2026-10-02，Folia）

- 按进程录音（process loopback）拿到的是**会话音量与静音生效之后**的信号。静音后录不到任何东西；会话音量设为 1e-4（−80 dB）后，录到的信号恰好缩小为 1/10⁴（float32，线性），乘以 10⁴ 即可无损还原。
- 未优化的“压低 → 录音 → ×10⁴ → 本程序输出”直通：延迟 49.8 ms，与系统实际输出的相关系数 1.0000，信噪比 80 dB（余量就是播放器自身漏出的 −80 dB），546 个 10 ms 块中 0 断音。
- 用户试听：中间听不出差别，与歌词对得上；接入和退出的那一刻有卡顿。卡顿来自约 50 ms 的时间差：接入时有约 50 ms 被重复，退出时有约 50 ms 被跳过。

## 3. 用户已确认的决定

1. **接管后一直保持。** 第一次打开去人声时接管播放器；之后关掉去人声只是切回原样直通（无缝）。只在退出应用、换播放器、或在设置里点“释放播放器”时才释放（各有一次轻微卡顿）。
2. **架构 B：独立的音频引擎进程**（`devocal-engine.exe`），应用通过命名管道控制它。

## 5. 进程划分与职责

| 进程 | 职责 |
|---|---|
| 应用（Tauri 后端 + 前端） | 界面、识调、Auto-Tune 控制、设置；启动、监视、重启引擎；根据媒体会话结果决定接管哪个播放器；启动时按恢复文件恢复 |
| 引擎 `devocal-engine.exe` | 只做音频：压低并持续盯住播放器进程树的会话、按进程录音并还原、处理（去人声/直通）、输出到播放器所在设备、切换淡化、报告状态与指标 |

**识调耦合：** 应用继续自己按进程录音做识调。引擎在状态里报告当前的衰减倍数（`attenuation`）及其计数（`attenuationEpoch`）；应用按倍数放大录到的数据。计数一变化，就作废分析缓冲（视作一次中断）。分离出的原唱暂不转发给应用。

## 6. 引擎内部

**采样率：**
- 内部采样率等于模型的采样率（StemgenRT 为 44.1 kHz）。
- 录音与输出都以共享模式、`autoconvert` 打开，由 Windows 做采样率转换。引擎内部不自行重采样。

**线程**（都申请 MMCSS“Pro Audio”优先级），之间用单生产者单消费者的无锁队列连接：

1. **录音线程**：
   - 事件驱动，process loopback 包含子进程树，格式为 float32 立体声；
   - 每个包乘以 `1/attenuation`；
   - 遇到不连续或时间戳错误标志时，通知处理线程重置模型状态。
2. **处理线程**：
   - 按模型规定的块长处理（StemgenRT 为 128 个采样）；
   - 去人声模式下调用模型、取伴奏；
   - 直通模式下把原信号延迟与模型相同的采样数，使两种模式在时间上对齐；
   - 每块记录推理耗时。
3. **输出线程**：
   - 事件驱动，输出到播放器会话所在的端点；
   - 有 `IAudioClient3` 时，使用其支持的最小共享周期；
   - 目标缓冲约为一个周期加一个处理块。

**切换：**
- 去人声 ↔ 直通：在处理线程中做 20 ms 等功率交叉淡化。
- 接管：约 30 ms 内分几步把会话音量降到 1e-4，同时我们的输出淡入。
- 释放：反向操作。
- 接管和释放时那约 50 ms 的重复或跳过无法避免，只用淡化遮盖。

**过载与断音：**
- 推理耗时的滑动平均超过块时长的 70%，或 1 秒内出现断音时，交叉淡化回直通，并报告原因 `overload`。之后不自动重试，等用户重新打开去人声或更换模型/档位。
- 断音时输出静音，前后做 5 ms 淡化，并计数上报。

**会话与设备跟随（每 0.5 秒检查一次）：**
- 播放器进程树新出现的会话，也压到 1e-4。
- 已压低的会话被用户或播放器调大时，重新压回 1e-4，并上报 `sessionOverridden`，界面提示“请调整本应用的音量”。
- 播放器会话换了端点，或输出端点失效时，输出线程重新绑定到新端点。

**模型接口：**

```text
trait Separator {
    fn sample_rate(&self) -> u32;
    fn hop(&self) -> usize;              // 每块帧数
    fn latency_frames(&self) -> usize;   // 固有延迟
    fn process(&mut self, input: &[f32], out_accompaniment: &mut [f32]); // 交织立体声，长度 = hop × 2
    fn reset(&mut self);                 // 切歌、不连续、模式切换后
}
```

- 第一版实现 `StemgenRt`：ONNX Runtime（Rust `ort`），CPU，`intra_op_threads` 默认为 1。
- 流式状态张量如何在块之间传递，按 `artifacts/separation-bench/src/`（`time_stemgen.py`、`stemgen_full.py`）与 `models/stemgenrt_streaming_models.json` 核实后实现。
- 伴奏的取法（模型直接输出伴奏，或用输入减去人声）也一并核实。
- 权重路径由应用通过 `set_model` 传入；第一版开发阶段指向本机已下载的 `artifacts/separation-bench/models/hop128.onnx`（SHA-256 `77164d6a…b3b8b9`）。在作者确认许可前，不随程序打包。

## 7. 状态、恢复与通信

**引擎状态：**
- `idle` → `attaching` → `active{mode: passthrough | devocal | fallback(reason)}` → `releasing` → `idle`。
- 任何一步出错，都先释放，再进入 `idle` 并报告错误。

**恢复文件：** `app_local_data_dir/devocal-restore.json`。
- 每次压低会话之前，先以原子写入（写临时文件后改名）记录：进程号、进程创建时间、会话实例标识、原音量、原静音状态、时间。
- 恢复成功后删除该文件。
- 恢复时：
  - 只在进程号与创建时间都匹配时才处理；
  - 只有当前音量仍为 1e-4 时才恢复为原值，否则保持现状（用户的设定优先）。

**谁来恢复：**

| 情况 | 处理 |
|---|---|
| 正常释放、退出应用 | 引擎恢复后退出 |
| 应用异常退出 | 引擎检测到管道断开或应用进程句柄已结束，恢复后退出 |
| 引擎异常退出 | 应用检测到引擎进程句柄已结束，按文件恢复；去人声仍开着时重启引擎（60 秒内最多重启 3 次，超过就停在原声并提示） |
| 两者都退出 | 应用下次启动时先按文件恢复 |
| 播放器退出 | 无需恢复；引擎回到 `idle` 并报告；应用识别到新播放器后再发 `attach` |

**管道：**
- 名称为 `\\.\pipe\autotune-helper-devocal-<应用进程号>`，ACL 只允许当前用户。
- 引擎启动参数带上应用的进程号，引擎同时监视这个句柄。
- 每行一条 JSON，带 `protocol: 1`。

命令（应用 → 引擎）：

| 命令 | 参数 |
|---|---|
| `hello` | 协议版本 |
| `attach` | `pid`、`createdAt`（FILETIME） |
| `set_mode` | `devocal: bool` |
| `set_model` | `id`、`path`、`device`（第一版只接受 `cpu`）、`threads` |
| `release` | — |
| `shutdown` | — |

事件（引擎 → 应用）：
- `state`：状态变化时立即发送；
- `metrics`：每秒一次，包含 `mode`、`latencyMs`（由缓冲与模型延迟估算）、`loadRatio`、`underruns`、`fallbackReason`、`attenuation`、`attenuationEpoch`；
- `error`：发生时发送。

## 8. 应用侧改动

- **后端新增 `devocal` 模块：**
  - 引擎管理：启动/监视/重启；启动时先恢复；命名管道客户端；
  - 用现有媒体会话与进程解析的结果发送 `attach`；
  - 向前端发事件。
- **识调**：`audio` 模块录到的数据按 `attenuation` 放大；`attenuationEpoch` 变化时作废分析缓冲。
- **界面：**
  - `PlayerControls.tsx` 的“去人声”预览按钮改为真实开关，第一次打开时接管；
  - 旁边显示状态，例如“去人声中 · 延迟 45 ms”“性能不足，已退回原声”“播放器音量被调整，请调本应用音量”；
  - 设置页加“释放播放器”按钮和接管说明，说明在音量合成器里播放器那一栏接近 0 是正常的。
- **打包**：引擎作为 Tauri 的 `externalBin` 附属程序。当前 `bundle.active=false`，开发构建时把引擎放在应用 exe 同目录。

## 9. 测试

- **引擎单元测试**（用假的会话控制和假的音频输入输出）：
  - 无锁队列的断音与溢出；
  - 交叉淡化增益曲线与直通延迟对齐；
  - 衰减还原；
  - 状态机所有转移；
  - 恢复文件的两道保护（进程号复用、音量已被改动）与原子写入；
  - 协议解析与版本不符时的拒绝；
  - 过载判定。
- **应用单元测试**：
  - 引擎管理（用假引擎）：重启上限、启动时恢复、管道断开；
  - 识调还原与作废。
- **真机集成测试**（每次执行前征得用户同意，用 Folia；测量方法同探测）：
  - 直通延迟 ≤ 40 ms，60 秒 0 断音；
  - 去人声延迟 ≤ 50 ms，记录 `loadRatio`；
  - 强杀引擎后 1 秒内音量恢复；
  - 强杀应用后引擎自行恢复并退出；
  - 播放器退出、切换默认设备。
- **试听**：由用户判断切换卡顿与去人声音质（代理指标不能替代试听，见 mid_b4 的教训）。

## 10. 风险与未决

- **StemgenRT 权重许可未声明**，训练数据为非商业许可。第一版只用于开发与自测，不分发权重；分发前须取得作者答复（询问邮件草稿已有，尚未发出）。
- **残留人声听得出来**（相对电平 −2～−11 dB）。音质提升靠后续子项目的模型选项。
- **只在本机 Folia 上探测过**。其他播放器、多会话播放器、独占模式播放器（独占模式下按进程录音可能失效）都需要实测。独占模式的播放器暂不支持，检测到时提示用户。
- **用户在音量合成器里调播放器那一栏**会被我们压回。这一点靠说明与提示解决，不做更复杂的映射。
- 本项目目录不是 git 仓库，设计文档无法提交到版本库。
