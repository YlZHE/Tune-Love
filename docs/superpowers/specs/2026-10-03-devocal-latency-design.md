# 去人声降延迟与接管体验：设计

日期：2026-10-03。状态：待用户审阅。
调研：`.superpowers/research/2026-10-03-latency.md`（不入库）。
上游：`docs/superpowers/specs/2026-10-02-devocal-engine-design.md`；验收：`E:\autotune helper\docs\2026-10-03_devocal-engine-acceptance-report.md`。

## 1. 目标与用户决定（2026-10-03）

- 范围：P0 到 P4 全做（测量 → 快速收益 → 原生采样率 → 低延迟档 → 接管体验）。
- 目标按档位设定，取代原规格中的“直通 ≤ 40 / 去人声 ≤ 50 ms”：

| 档位 | 适用设备 | 直通 | 去人声 |
|---|---|---|---|
| 标准（默认） | 任何设备 | ≤ 55 ms | ≤ 58 ms |
| 低延迟 | 支持 ≤ 3 ms 共享周期的设备 | — | ≤ 40 ms |
| 稳定 | 弱电脑、易断音的设备 | 标准 + ≤ 10 ms | 标准 + ≤ 10 ms |

  接管与切换的要求：不出现超过 10 ms 的空洞；内容跳变不超过当前延迟 D；新播放器启动的场景听不出接管。
- 不变的硬约束：
  - 不对播放整体加延迟换前瞻；
  - 不注入、不装驱动；
  - 不跑满 CPU/GPU；
  - 永远不比原音量响；
  - 播放器音量必须始终能恢复。

## 2. 现状（基线）

- **实测 75.1 ms 的条件**：直通，但之前开过一次去人声，所以留着 441 帧（10 ms）的常驻余量。
- **从未开过去人声的直通**：估计约 65 ms，P0 复测确认。
- **我们自己的部分**，约 43 ms：
  - 采集包长 10 ms；
  - 环形缓冲 A 约 1.5 ms；
  - 直通延迟线 2.9 ms；
  - 环形缓冲 B 等待 0～10 ms；
  - 渲染目标 12.9 ms；
  - 余量 10 ms。
- **系统部分**，约 32 ms：
  - 进程回环交付晚 12～16 ms；
  - 混音量化 0～10 ms；
  - 两次采样率转换；
  - 引擎本身约 1.3 ms。
- **接管时的听感**：先重复约 D（75 ms）的内容，接着有约 100～130 ms 几乎没声。后一段来自保守增益窗口：音量 30 ms 内就降到 1e-4，补偿增益却要等 100 ms 才升上去。之前说的“采集中断 0.3 s”，是诊断日志的误读。

## 3. 分阶段设计

### P0 测量与诊断

1. **诊断日志防误读**：每行带运行编号和单调时间戳；停止时的最后一行标注为“partial”。
2. **被动拆分探测**：新增一个开发用示例程序，录端点回环和进程回环时，记下每个包到达时的 QPC，并按内容对齐，得出进程回环的真实交付延迟。
   - 第一次：不开小周期流；
   - 第二次：本程序以最小周期打开一个静音渲染流。这会改变该端点的引擎周期，需要用户授权。

   两次结果合起来，回答“进程回环的包会不会随周期变小”，这决定 P3 能省多少。
3. **只读设备查询**：对每个输出端点读取 `GetMixFormat` 和 `GetSharedModeEnginePeriod`，列出哪些设备支持低延迟档。
4. **基线复测**（用释放跳变法，每种状态 5 次，报中位数和最大值）：
   - (a) 从未开过去人声的直通；
   - (b) 开、关一次去人声后的直通；
   - (c) 去人声稳定运行。

   同时用实测数据校准 `SYSTEM_PATH_PERIODS`，让引擎自报的延迟贴近实际。

### P1 快速收益

- **O1 余量衰减**：
  - 预缓冲只在 `WarmingUp`/`FadingIn` 期间生效；
  - 抖动余量在连续 5 s 没有欠载后，借现有修剪逻辑（先淡出、再跳过、再淡入）降回 `period + hop`，跳过点尽量选在低能量的块上；
  - 之后再出现抖动欠载，规则照旧：余量加回去，上限 441 帧。
- **O2 到达即写**：渲染线程同时等待两个事件，“设备事件”和“处理完成”（`WaitForMultipleObjects`），数据一到就写入。写入者仍然只有渲染线程。
  - 重新推导目标：两次写入之间，队列的最低点也不得少于一个周期。
  - 时钟漂移仍然靠修剪处理。
- **R2 按电平确认增益**：接管时，采集增益不再按固定的 100 ms 窗口升高，改为按块判断，同时满足两个条件才对这一块用高增益：
  - 该块的电平相对接管前的几块，按已经下发的音量步骤确实降了下来（容差 ±6 dB）；
  - 该块之前的所有音量都已下发。

  以下情况退回现有的 100 ms 窗口：
  - 音乐本身是静音；
  - 判定超时（> 150 ms）；
  - 电平不符。

  安全检查（峰值超过 1.5 就整块静音）保留。
- **预期**：约 55～60 ms；接管时的空洞不超过 10 ms。

### P2 按设备原生采样率运行

- **O3**：
  - 引擎采样率改为运行时取设备的混音格式（48 kHz 等），`SAMPLE_RATE` 常量改成运行时参数。441 帧等常量改为按时间换算。
  - 采集和输出都使用混音格式，不再做系统采样率转换。只有去人声在模型前后用 rubato 做 48k↔44.1k 转换（不分配内存的固定块模式，用 `output_delay()` 计算延迟）。StemgenRT 是按 44.1 kHz 训练的，不能直接喂 48 kHz。
  - 直通延迟线必须等于“重采样 + 模型”的总延迟，保证开关去人声时两路对齐。
  - 混音格式超过两个声道时，只处理前两个声道，其余声道原样直通。
  - 采集和输出的采样率不一致时（例如设备在接管期间改了混音格式），重新接管。
- **预期**：约 52～58 ms；去人声比直通多 1～3 ms。

### P3 低延迟档与三档设置

- **O4**：当混音格式是任意 float 时，渲染使用 IAudioClient3 的最小共享周期（必须先完成 P2）。下列情况自动退回标准档，并在状态里写明原因：
  - 周期被其他程序锁定（`AUDCLNT_E_ENGINE_PERIODICITY_LOCKED`）；
  - 设备不支持。
- **三档设置**（设置页，存在应用设置里，通过管道下发给引擎）：
  - **低延迟**：最小周期。只在设备支持时可选。说明里写明：会让同一设备上的所有程序都切换到小周期，略增耗电，可能更易断音。
  - **标准**（默认）：10 ms 周期。
  - **稳定**：标准档加 1 个 hop 的固定余量，修剪阈值放宽。

  出现欠载导致退回原声时，自动建议改用“稳定”档，不自动切换。
- **预期**：在支持的设备上约 25～45 ms，取决于 P0 的探测结论。

### P4 接管体验

- **R1 在出声前接管**：
  - 应用这边，只要播放器进程或会话出现、尚未开始出声，就提前确定目标并接管。暂停期间也可以接管，D 规则已经保证暂停时不会放开会话。
  - 沿用现有的 PID 和身份核验。

  效果：在新播放器启动的场景下，听不出接管。
- **R3 用空隙代替重复**：接管时丢掉渲染队列里交接点之前的内容（约 D），两侧各做 5 ms 淡化。听感从“回跳”变成很短的停顿；降延迟之后 D 约 30～55 ms。
- **R4 保持输出流**：在不同播放器之间重新接管、输出端点又不变时，不重开渲染流和环形缓冲 B，只换采集。`AudioHandle` 要拆成采集和输出两部分，生命周期分开管理。

## 4. 验收（每项真机步骤都须单独授权；执行前核验进程身份）

- **基线与各阶段**：每阶段用调研 §4 的流程，状态 (a)(b)(c) 各 5 次释放跳变，报中位数和最大值，对照第 1 节的目标。
- **重新接管**：录一次接管，用 `attachLatencyMs` 测重复长度；断音计数（10 ms 块比相邻块低 30 dB 以上）量出空洞长度。
- **回归**：
  - 每个档位连续 60 s 0 断音；
  - `loadRatio < 0.7`；
  - 引擎 CPU 记录在案；
  - 切换设备、暂停/继续、播放器退出与重开、强杀引擎：A、B、D、E 的复测全部通过；
  - 用户试听接管、释放和切换。

## 5. 测试

- **单元测试**：
  - O1 余量衰减与回收；
  - O2 写入时机与队列最低点；
  - R2 电平判定的边界：静音、超时、电平不符时退回，以及“永远不比原音量响”的不变量；
  - P2 采样率参数化，以及在 44.1/48/96 kHz、多声道下的直通与去人声对齐（离线比较）；
  - rubato 往返的延迟与幅度；
  - P3 退回逻辑（用假的 IAudioClient3 返回锁定或不支持）；
  - 三档设置的序列化；
  - R3 交接点丢弃与淡化；
  - R4 拆分后的生命周期。
- **CI**：不需要设备的测试全部进 devocal 任务。

## 6. 不做

- 模型本身的加速，比如 int8 量化或更小的模型。这属于模型子项目，需要先做离线质量对比。
- 独占模式、虚拟声卡、驱动。
- 改动 Auto-Tune 相关代码。

## 7. 风险

- **P2 改动面大**：441 帧等常量散布在各处。按“先参数化、44.1 kHz 下行为完全不变，再接通 48 kHz”两步走。
- **低延迟档影响整个设备上的程序**：只在用户明确选择后启用。
- **R2 判定错误时可能放大未压低的声音**：设计上带保守退回，并有安全检查兜底；用单元测试和真机计数（安全检查静音块数）验证。
