# 拿不准时用 Chromatic，标题只显示最终 Key / Scale：设计

日期：2026-10-04。状态：待用户审阅。

## 背景与用户决定

用户循环播放一首 F 小调、带多利亚色彩的歌，看到两处显示互相矛盾：标题左上角有时是“F 小调”，中间的建议却是“G♯ 大调”。原因如下：

- 标题来自 libKeyFinder 的传统调性检测。
- 建议来自音集匹配（`src-tauri/src/key_detection/scale_match.rs`）。它只比较哪组 7 个音能覆盖证据，不判断主音。F 小调与 A♭（G♯）大调是同一组音，打分相同；平局时取排在前面的大调名。两者写进 Auto-Tune 后修音完全相同。
- 真正的风险：歌里 D 与 D♭ 都常用（F 小调借用多利亚的 D）时，任何一组 7 个音都盖不全，总有一个常用音会被误拉。

用户 2026-10-04 的决定：

1. **支持 Chromatic**，在三种场景使用：拿不准时自动切换；开头还没有证据时先用；界面上提示拿不准。
2. 拿不准时，**误拉比不修音更糟**。界限按“宁可不修，也不误拉”来定。
3. **推荐与标题合并**，最终只显示一个 Key / Scale，写法与 Auto-Tune 一致，例如 `F Minor`、`G# Major`、`F Chromatic`。

本决定取代 AGENTS.md 中 2026-10-02 的“不使用 Chromatic”及“不得以退回 Chromatic 防误拉”两条。旧条目保留为历史，并在旁边注明已被取代。

历史提醒：frontend-b 第一、二轮的旧规则会退回 Chromatic，部分歌因此全程或长时间不修音（例如“紧身衣”全曲未收窄）。所以本设计要求逐首统计 Chromatic 时长，并列出全程 Chromatic 的歌，交由用户判断，不能只看误拉率。

## 不在范围内

- Dorian、Mixolydian 等调式名。它们与大调是同一组音的不同起点，不增加覆盖能力。
- 和声小调、五声音阶、布鲁斯等其他音组。frontend-b “放宽音阶”结论是弊大于利，用户已决定不再考虑。
- 低音加权、节拍加权、鼓点抑制等新的证据前端。
- 按片段判断调性。

## 设计

### 1. 判断“拿不准”：盖不住的比例

匹配器已有逐音级证据权重 `weights`（含均匀先验 `alpha`）。对当前最合适的 7 音集合 `S`，定义：

```
uncovered(S) = Σ weights[pc]，pc 不属于 S
```

它表示：如果写入 `S`，证据中有多少比例落在集合外，也就是会被拉到别的音上。

状态机，所有参数离线定数后冻结：

- **Chromatic → 某集合**：同时满足
  - 本次播放的有效证据 ≥ `MIN_SECONDS`；
  - 最佳集合 `uncovered < EXIT`；
  - 这两个条件持续 `EXIT_HOLD` 秒。
- **某集合 → Chromatic**：最佳集合 `uncovered > ENTER`，且 `ENTER > EXIT`，两条线之间留出空隙。
- 两个集合之间的切换沿用现有迟滞规则（`margin`），不变。
- 整首歌证据持续累积，不按片段重置。

开头策略也由这套规则自然得出：证据少于 `MIN_SECONDS`，或先验占比还高时，`uncovered` 必然偏高，结果就是 Chromatic。

### 2. 结果类型

`AutoTuneTarget` 扩展如下（Rust 与 TS 同步）：

- `scale`：`major | minor | chromatic`。
- `key`：可为空。完全没有证据时为空；只要有过候选，就是排第一的候选主音。Chromatic 时写入这个 Key，以后切回 Major/Minor 时不用再改 Key。
- `candidate`：排第一的 Major/Minor 候选，即使当前是 Chromatic 也给出，用于提示。
- `uncovered`：当前最佳集合盖不住的比例。
- `uncoveredNotes`：集合外权重最高的音名（最多 2 个），用于提示，例如“D 与 D♭ 都常用”。
- `evidenceSeconds`、`source` 保持不变。

转调函数 `transpose` 对 Chromatic 只平移 Key。

### 3. 关系大小调定名

最佳集合确定后，主音名的定法：

- 如果 libKeyFinder 当前**已稳定**的结果，其主音和大/小调属于这组音的大调或关系小调，就采用它的叫法。例如它判断为 F 小调，就写 `F Minor`，不写 `G# Major`。
- 否则沿用这组音上次的叫法；第一次则取大调名（即现有行为）。
- 定名变化只在集合确定或 libKeyFinder 稳定结果变化时发生，不逐帧抖动。音组不变时改名，同样需要重新写入，但修音不变。

### 4. 缓存

`song_cache` 允许保存 `chromatic`，同时保存 `candidate`，以免“拿不准”的结论在重播时丢失：

- 重播一首曾经拿不准的歌：开头直接用 Chromatic。本次证据达到 `SEED_HOLD_SECONDS` 后按规则重新确认。
- 重播一首曾经确定的歌：照现在的做法立即采用缓存的集合。
- 旧缓存文件（只有 major/minor）仍能读取。

### 5. 自动写入

- 开关打开时：
  - 歌曲开始、还没有任何证据，只写 `Scale = Chromatic`，不动 Key；
  - 之后按结果写入 Key + Scale。
- 每个 (连接, 曲目, Key/Scale 组合) 只写一次；失败不自动重试（现有规则不变）。
- Chromatic 的选项值取自插件自身声明的选项表 `reference/profiles/*.json` 中的 `"Chromatic"`，不猜参数。

### 6. 界面：标题只显示最终 Key / Scale

- 合并 `KeyTitle` 与 `AutoTuneTargetStatus`。标题显示当前结果，写法与插件选项一致：
  - `F Minor`
  - `G# Major`
  - `F Chromatic`
  - 尚无候选时显示 `Chromatic`
  - 没有曲目或尚未开始分析时显示 `Tune Love`
- 删除中间的“建议 … · 状态”一栏。以下信息移入标题的悬停提示：
  - 写入状态（已写入、写入中、写入失败、自动写入已关闭）；
  - 已分析秒数；
  - 是否来自上次播放；
  - 拿不准时说明原因，并给出排第一的候选，例如：“拿不准：D 与 D♭ 都常用，暂用 Chromatic。排第一的候选是 F Minor。”
- 写入失败时，标题旁显示一个小标记。
- libKeyFinder 的结果不再单独显示，只用于第 3 节的定名。
- 设置页“自动写入”的说明文字改为新规则。

### 7. 错误与边界

- 插件选项表缺少 `Chromatic` 时，降级为现行行为：只在 Major/Minor 中选，并在提示里说明。
- 静音或无效证据仍被忽略。只要不满足退出 Chromatic 的条件，就保持 Chromatic。
- 切歌时重置，与现状相同。

## 定数与验收（离线）

使用现有 `experiments/scale-match/` 工具链及逐帧打分。

- **新口径**：分别统计以下各项，不再合成一个只把 Chromatic 记为失败的分数：
  - 误拉率；
  - 修音覆盖率（可评估帧中处于 Major/Minor 的比例）；
  - Chromatic 时长占比；
  - 首句综合分；
  - 每首切换次数；
  - 全程 Chromatic 的歌单。
- **开发集**：以往任何一轮用过的全部歌曲（试点、留出集 holdout、frontend-b 各批，以 `work/scale-match-20261002/preregistration.md` 为准）。在网格上选取 `ENTER / EXIT / EXIT_HOLD / MIN_SECONDS`。
  - 选取规则：误拉率最低；同等误拉下，修音覆盖率最高。
  - 预登记写在看到新歌结果之前。
- **检验集**：按既有方式（SHA-256 排序）选出一批未用过的新歌，共 10 首，比较新规则与现行 majmin 规则。
- **通过条件**：新歌上误拉率低于 majmin，且逐首列出 Chromatic 占比与全程 Chromatic 的歌。是否接受这个“少修换少误拉”的代价，由用户根据报告决定。
- **诊断案例**：用户循环播放的这首歌如果在曲库中，单列它的结果。它不进入检验集。

## 测试（代码层面）

- `scale_match`：
  - 没有证据时为 Chromatic 且没有 Key；
  - D 与 D♭ 同时强时进入 Chromatic，并给出候选；
  - 退出需要满足持续时长；
  - 两条线之间不会来回跳；
  - 关系大小调按 libKeyFinder 的稳定结果定名；
  - 缓存中的 Chromatic 在重播开头生效；
  - 旧缓存可以读取。
- 自动写入：开头只写 Scale；Chromatic 使用插件选项值；选项表缺少 Chromatic 时降级。
- 界面：标题四种文字；提示内容；写入失败标记；中间栏已移除。现有 Playwright 用例同步更新。

## 后续（用户 2026-10-04 决定）

- 本设计只用混音证据，先落地。
- 不引入直接判断调式的分类模型。它只改善大小调的叫法，而关系大小调认错本来就不会误拉；它也解决不了 7 个音盖不全的问题。
- 下一步按既定顺序，离线实测原唱音高模型 PESTO：分离出的人声 → 音高 → 音级证据。证明能降低误拉之后，再把原唱证据并入“盖不住的比例”的计算。这一步另立设计。
